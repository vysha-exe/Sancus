## Goal

Make one hackathon path work reliably:

1. Issue a real Marqeta sandbox card and show its provider-issued last four digits.
2. Create and settle an inbound PayZu Pix collection.
3. Show the inbound payment in activity and increase a seeded BRL balance projection.
4. Issue controlled Pix spending access to an employee.
5. Resolve and pay a merchant Pix QR through PayZu.
6. Update the employee's used limit, activity, and projected BRL balance.

## Locked decisions

- Approach A only: Marqeta plus inbound/outbound Pix is the critical path.
- Regional balance is a seeded read projection, not a new treasury engine.
- Provider sandboxes are not labeled simulated; deterministic fallbacks are.
- Fallbacks run only when credentials are missing or `SANCUS_DEMO_FALLBACKS=true`; provider errors remain errors.
- Settlement uses 3-second polling for the active pending operation, stopping at a terminal state or after 2 minutes.
- Verification is local black-box testing only. No CI or new automated test suite is required.
- If a provider succeeds and the database insert fails, the demo stops and is manually reset. Provider reconciliation is deferred.

## Regional BRL balance projection

Do not create a mutable balance ledger for the hackathon. Compute:

```text
available BRL = seeded opening BRL
              + settled inbound Pix collections
              - settled outbound Pix payments
```

- Read the opening amount from `SANCUS_DEMO_BRL_OPENING_BALANCE_MINOR`.
- Sum only the authenticated user's settled `PIX` collection/payment rows.
- Expose a small authenticated regional-balance API and hook.
- The teammate-owned cross-border integration later replaces the opening-balance loader or writes the agreed base amount; the UI contract remains stable.
- Insufficient projected balance declines outbound Pix before calling PayZu.

This avoids double-posting, new accounting tables, and coupling to unfinished cross-border code.

## Implementation sequence

### 1. Make provider truth explicit

- Add one shared `SANCUS_DEMO_FALLBACKS` configuration helper.
- A successful real Marqeta or PayZu sandbox call persists `simulated: false`.
- Deterministic Marqeta and PayZu fallback results persist `simulated: true` and use stable `SIM-*` identifiers.
- Missing credentials may use fallback; sandbox rejection, timeout, or malformed responses remain visible errors unless the explicit fallback flag is enabled before the request.
- Show **Sandbox** or **Simulated** consistently in cards, collections, Pix payments, and activity.
- Add a demo-readiness response or visible diagnostic that reports whether Marqeta and PayZu are configured before presenting.

### 2. Add the seeded BRL projection

- Add a server helper that loads the opening BRL amount and sums settled inbound/outbound Pix rows for the authenticated user.
- Add an authenticated read endpoint returning `country`, `currency`, `availableMinor`, `openingMinor`, `inboundMinor`, `outboundMinor`, and `updatedAt`.
- Check projected availability immediately before outbound Pix provider submission.
- Add a lightweight client hook/card so Receive, Spending, or Home can show the current BRL amount.
- Emit a shared client refresh event after a collection or payment reaches a terminal state.

### 3. Consolidate inbound Pix

- Keep `/api/sancus/collections` and `CollectionDemo` as the only primary inbound collection path.
- Default its rail selector to Pix.
- Remove `LocalCollectCard` and the static QR placeholder from the primary Receive layout.
- Poll only the selected pending collection every 3 seconds; stop when settled/failed/expired/cancelled or at 2 minutes.
- On terminal state, refresh activity and the BRL projection.
- Keep QRIS and PromptPay selectors available but do not spend demo time changing or verifying them.

### 4. Finish outbound Pix access and payment

- Rename employee-facing “Local QR”/“issue QR” copy to **Pix access** for Brazil.
- Preserve create, pause, resume, limit, and revoke behavior.
- Resolve a real merchant Pix copy-and-paste payload before enabling payment.
- Reject inactive access, monthly-limit excess, and insufficient projected BRL before PayZu submission.
- Poll a pending Pix payment every 3 seconds with the same terminal/timeout rules.
- On terminal state, reload spending-method usage, activity, and the BRL projection.

### 5. Finish card presentation

- Require configured Marqeta credentials for the primary demo readiness check.
- Keep fallback available for development, but display a visible **Simulated** badge.
- Show only persisted provider-issued cards as live results; remove or label hard-coded cards as sample data.
- Show last four, employee, currency, monthly limit, status, and sandbox/simulated source.
- Do not add card transaction webhooks or card purchase simulation to Approach A.

### 6. Black-box verification and demo reset

- Apply the existing card and local-rail migrations to the demo Supabase project.
- Prepare one demo user, employee, opening BRL balance, known Pix amount, and reset steps.
- Run the real-sandbox browser flow below end to end.
- Repeat with explicit fallback mode and verify every fallback artifact is labeled **Simulated**.
- Record screenshots and provider IDs/last four used in the final rehearsal.

## Black-box runbook

1. Reset/seed the demo account and start the app with Marqeta and PayZu sandbox credentials.
2. Confirm readiness reports both providers configured and fallback disabled.
3. Issue a card to the seeded employee; verify a non-`SIM` provider record, real last four, monthly limit, and no Simulated badge.
4. On Receive, create a Pix QR; pay it in PayZu sandbox; wait for automatic settlement; verify activity credit and BRL balance increase.
5. Issue Pix access to the employee with a known monthly limit.
6. On Spending, resolve a known merchant Pix QR and pay it; verify settlement, used allowance, activity debit, and BRL balance decrease.
7. Pause access and verify another payment is declined before PayZu; resume it.
8. Lower the limit below a test payment and verify the limit decline; restore it.
9. Enable fallback mode with sandbox credentials absent; repeat card, inbound Pix, and outbound Pix; verify stable results and Simulated labels everywhere.
10. Reset again and rehearse the exact stage sequence without developer tools.

## Failure modes and handling

| Failure | Planned behavior |
| --- | --- |
| Missing provider credentials | Explicit deterministic fallback with Simulated label |
| Expired PayZu token | Actionable error; no automatic fallback unless demo mode was enabled before the request |
| Provider timeout/rejection | Visible recoverable error; no false success |
| Pending status never settles | Stop polling at 2 minutes; retain manual refresh |
| Insufficient employee limit | Reject before provider call |
| Insufficient projected BRL | Reject before provider call |
| Provider succeeds, DB insert fails | Stop and manually reset/reconcile in sandbox; accepted hackathon risk |
| Cross-border balance event unavailable | Use configured opening BRL seed; keep the same read contract |

## Performance review

- Bounded polling touches only the active pending record and stops after 2 minutes.
- Activity and balance refresh only on navigation or the shared data-changed event.
- Balance aggregation scans only the authenticated user's settled Pix rows; existing user/status indexes are sufficient for hackathon volume.
- Do not add caching, queues, workers, or realtime subscriptions for this scope.

## NOT in scope

- Card purchase authorization/transaction webhooks — card issuance is enough for Approach A.
- Production reconciliation after provider-success/database-failure — manually handled in sandbox.
- Automated tests or CI — replaced by the approved black-box release gate.
- Brazilian supplier-bank provider integration — provider is still TBD.
- Xendit changes — SEA payout is outside the critical Brazil path.
- QRIS/PromptPay verification or redesign — remain available but off-stage.
- Deleting duplicate collection code — unmount it now; delete after the hackathon.
- Production accounting, FX, compliance, disputes, KYC, or PCI scope.
